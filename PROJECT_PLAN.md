# mahno-tv-manager — план проекта

Автономный менеджер виртуального телеканала с эстетикой нулевых: собирает эфир из
мультсериалов, вставляет рекламу и заставки, накладывает лого и бегущую строку,
портит картинку и звук под VHS/аналоговое ТВ — и всё это вживую, 24/7, с техперерывом
ночью.

## 1. Архитектурное решение

Выбран стек: **Python** для "мозга" системы + **OBS Studio** как движок
рендеринга/компоситинга/вывода потока, управляемый через `obs-websocket` (v5).

Почему так:
- OBS уже умеет то, что дольше всего писать самому: RTMP/вывод потока, переключение
  сцен и источников, хостинг VST 2.x на аудиодорожке, экосистема фильтров.
- Python даёт скорость разработки для того, что реально сложно в этом проекте —
  логику планирования сетки вещания, ротацию повторов, работу с Gemini API — без
  необходимости оптимизировать низкоуровневый рендеринг руками.
- Компромисс: часть "настоящего реалтайма" (эффект VHS, аудио-VST) фактически будет
  жить внутри OBS как фильтры, а не как код на Python. Python-часть — это диспетчер
  ("Director"), а не рендерер.

### Компоненты

│  • ротация повторов / ивенты  │                              │   - Bumper             │

│  • контроль дрейфа времени    │                              │   - лого (image)       │
│  • БД: каталог, история эфира │                              │   - бегущая строка     │
└─────────────────────────────┘                              │     (browser source)   │

                                                                │   - VST-цепочка аудио  │
                                                                │  Выход: RTMP/запись    │
                                                                └───────────────────────┘

**Статус плейаут-контроллера (Фаза 3): реализовано** (`director/playout.py`,
`obs_playout.py`, `run_playout.py`). Подход — не событийный (не ждём от OBS
"клип закончился"), а поллинг раз в 3с: на каждом тике спрашиваем "что по
program_log должно идти в эфире прямо сейчас" и сверяем с тем, что реально применено
к OBS; расхождение — сразу переключаем. Это даёт коррекцию дрейфа "бесплатно" —
ошибка не накапливается, потому что каждый тик пересчитывается от абсолютного
времени, а не от "сколько прошло с прошлого переключения"; и это же естественно
реализует жёсткий вход в техперерыв (что бы ни играло, в 05:00 МСК на следующем тике
переключение на OFF_AIR произойдёт независимо от состояния текущего клипа).
`ensure_scenes()` создаёт нужные сцены/источники в OBS сам, если их нет (идемпотентно).
Живой прогон на реальном OBS 32.0.4 вскрыл реальный баг: `GetInputKindList` с
`unversioned=true` отдаёт "витринные" имена кайндов (`color_source`), а `CreateInput`
принимает только versioned id (`color_source_v3`) — поправлено, `unversioned=false`
используется для реального резолвинга. Сквозная проверка (ad → bumper → off_air)
прогнана вживую с независимым опросом состояния OBS на каждом переходе.

**Статус оверлеев (Фаза 4): реализовано, кроме визуального подтверждения бегущей
строки** (`director/gemini_client.py`, `ticker_content.py`, `ticker_server.py`,
`run_ticker.py`, `overlays.py`). Ключи Gemini — в гитигнорнутом `secrets.json`
(шаблон `secrets.example.json`), никогда не в коде/конфиге, который коммитится.
Ротация: сперва все ключи на `gemini-3.5-flash`, затем все ключи на
`gemini-3.1-flash-lite` (лимиты см. в переписке — 5/20 и 15/500 RPM/RPD
соответственно), при пустом ответе/ошибке — следующая комбинация, при полном
исчерпании — статичный fallback-список. Обновление пула — идемпотентно раз в
сутки по дате МСК. Ticker вынесен в отдельный локальный HTTP-сервер
(`http://127.0.0.1:8765/` + `/ticker.json`), а не статический файл — иначе
browser source в OBS не может обновлять контент без CORS-проблем file://
(эта проблема была видна ещё в спайке Фазы 0). Лого позиционируется в правый
нижний угол через `OBS_BOUNDS_SCALE_INNER` — не нужно знать реальное разрешение
файла лого заранее. Живая проверка на реальном OBS 32.0.4 прошла для лого
(скриншот сцены подтвердил точное позиционирование/масштаб) и для реального
вызова Gemini (боевой ключ, 20 строк в аутентичном стиле нулевых). Ticker
`browser_source` сначала давал чисто белый скриншот (даже для тривиального
`data:text/html` с красным фоном) — что навело на ложный след про CEF/аппаратное
ускорение. Реальная причина: `ticker_server` запускался только внутри коротких
тестовых скриптов Phase 4 и умирал вместе с ними, так что к моменту скриншотов
browser source в OBS стучался в закрытый порт. После запуска `run_ticker.py` как
постоянного фонового процесса и `PressInputPropertiesButton`/`refreshnocache`
строка подтверждена скриншотом сцены — видна и скроллится. **Важно для
эксплуатации**: `run_ticker.py` (как и `run_playout.py`) должен быть постоянно
запущенным процессом, а не разовым скриптом — это войдёт в Фазу 6
(вывод/устойчивость, автозапуск/watchdog).

**Разрешение канвы: PAL SD, 720x576 @ 25fps.** Изначально OBS стоял на HD
(1920x1080@60). Раз эстетика — нулевые, разрешение тоже должно быть периода: в
России эфирное/кабельное ТВ тех лет — PAL, 720x576 (в отличие от NTSC 720x480 в
США/Японии). Применено через `SetVideoSettings` (base = output = 720x576, без
даунскейла). Из-за этого пришлось пересчитать геометрию оверлеев:
`overlays.py` изначально задавал размер лого/бегущей строки в **абсолютных
пикселях**, откалиброванных под 1920x1080 (220x110 для лого) — на 720x576 та же
рамка в пикселях съедала бы ~30% ширины кадра. Переведено на **доли канвы**
(`LOGO_WIDTH_FRACTION` и т.д.), пересчитывается на лету из `GetVideoSettings`
при каждом вызове `ensure_logo`/`ensure_ticker_source` — теперь корректно при
любом разрешении. Подтверждено скриншотом сцены на 720x576: лого (реальный —
пользователь подставил `RENTV2002.png`, логотип РЕН ТВ образца 2002 года)
пропорционально небольшое в правом нижнем углу.

## 3. Модель данных (черновая)

- **Library** — папки с мультсериалами: сериал → сезон/эпизод → файл, метаданные
  (длительность, разрешение, дата добавления, теги/жанр).
- **AdPool** — рекламные ролики (теги: категория, длительность, "устал" ли ролик —
  счётчик показов за период).
- **BumperPool** — заставки/лого-станции/межпрограммные ID, отдельно от рекламы.
- **ScheduleBlock** — шаблон дневного/недельного блока (напр. "утренний блок мультов",
  "вечерний блок", "марафон по выходным").
- **ProgramLog** — сгенерированная сетка вещания на N дней вперёд (как настоящий
  traffic log): время начала, тип элемента (программа/реклама/заставка/техперерыв),
  ссылка на файл, статус (запланировано/сыграно).
- **PlayHistory** — что и когда реально вышло в эфир — основа для логики повторов
  (не повторять эпизод раньше, чем через X дней; не ставить один и тот же ролик
  дважды в одном рекламном блоке и т.д.).
- **TickerPool** — сгенерированные Gemini заголовки с датой генерации и статусом
  использования.

## 4. Алгоритм сетки вещания ("Traffic")

Логика, которая должна вести себя как у настоящего медиаменеджера:

1. **Слоты и блоки.** Сутки делятся на именованные блоки (напр. 10:00–13:00 —
   утренний блок, 13:00–18:00 — дневной, 18:00–23:00 — вечерний прайм, 23:00–05:00 —
   ночной повтор-блок), каждый со своими правилами подбора контента (какие
   папки/сериалы допустимы, целевая аудитория повторов vs. премьер).
2. **Off-air окно 05:00–10:00 МСК.** Жёстко зарезервировано — никакого контента,
   отдельная сцена/заглушка (тестовая таблица, "профилактика на канале" — в духе
   нулевых). Таймзона МСК фиксированная (UTC+3, без переходов на летнее время).
3. **Ротация и повторы.** Для каждого сериала — минимальный интервал до повтора
   эпизода, ограничение "не более N эпизодов одного сериала подряд без разбавления",
   учёт уже показанного (PlayHistory) при выборе следующего.
4. **Ивенты.** Отдельный слой поверх обычной сетки: марафоны выходного дня,
   "премьерные" вставки новых серий, тематические блоки по праздникам — задаются как
   переопределения обычных правил на конкретную дату/диапазон.
5. **Рекламные блоки.** Между программами (и опционально — внутри длинных программ,
   если заданы точки разбива) вставляется под ("pod") из роликов из AdPool,
   подобранный так, чтобы сумма длительностей точно попадала в целевой хронометраж
   слота (добивка более короткими роликами/заставками при необходимости).
6. **Заставки.** Между программным контентом и рекламными блоками — bumper/ID
   канала, обязателен на входе/выходе из рекламного блока (как у реальных станций —
   "мы вернёмся после этих сообщений" / "мы снова в эфире").
7. **Генерация.** Сетка строится заранее на N дней вперёд (напр. на 3 дня), с
   возможностью пересборки хвоста при ручном вмешательстве (добавили новый эпизод в
   папку — пересчитать ещё не сыгранные дни).

**Статус: реализовано** (`director/blocks.py`, `rotation.py`, `ad_pods.py`,
`scheduler.py`). Отличия от исходного черновика: шаблоны блоков живут в коде, а не в
БД (проще для ревью и правки, пока нет веб-панели — см. Фазу 7); ротация эпизодов —
не "least recently played", а курсор по (season, episode) на сериал (следующий после
последнего вышедшего в эфир, с циклом при исчерпании), что ближе к тому, как реально
работают синдикационные повторы. Проверено сквозным тестом на синтетической
медиатеке: сутки собираются без наложений и пропусков, вход в техперерыв всегда
ровно к 05:00 МСК (эпизод, не влезающий целиком, просто не берётся), выходной
марафон-ивент подтверждён живьём через `show_schedule`.

**Библиотека загружена на реальном контенте (F:\REN-TV, 12 тайтлов, 421 серия +
1 рекламный ролик + 3 заставки)** — попутно вскрылось и закрыто несколько проблем
сканера, которых не было видно на синтетических тестах:
- `series_root` указывал на весь диск, где вперемешку лежат сериалы, сырьё для
  монтажа (Ads/), готовые ролики (Bumpers/) и даже кэш проекта DaVinci Resolve —
  добавлен аллоулист `config.active_series`, сканируются только явно
  перечисленные папки.
- Ads и Bumpers физически в одной папке (готовые ролики после монтажа сырья) —
  `scan_flat_root` получил опциональный `classify(path)`, определяющий
  принадлежность файла по префиксу имени (`ad-in-*`/`ad-out-*` → бампер,
  `ad-block-*` → реклама), без дублирования в обе таблицы.
- W.I.T.C.H. (Charodejki) разложен по подпапкам "N sezon" без номера сезона в
  имени файла — сканер теперь читает сезон из родительской папки, если она
  совпадает с этим паттерном.
- Разномастная нумерация серий (Courage — "1.01.", Futurama — "1ACV01") ломала
  парсер, хватавший только первую цифру и сталкивавший все серии на одном
  номере (фактический порядок ротации не страдал за счёт сортировки по имени
  файла как tie-breaker, но `show_schedule` показывал "S01E01" для всего) —
  добавлены точечные паттерны под оба формата.

**Премьеры vs рандомные повторы, рекламная логика под REN TV — реализовано.**
`series.rotation_mode` (`'sequential'` по умолчанию, `'random'` — курируется
через `config.random_rotation_series`, применяется после каждого скана).
`rotation.py`: sequential — прежний курсор по (season, episode); random —
случайный выбор из "залежавшейся" половины каталога сериала (никогда не
выходившие в эфир эпизоды сортируются первыми), не строго детерминированный
выбор одного самого старого. Рекламные паузы (`scheduler._insert_ad_break`)
теперь адресно берут `ad_in`/`ad_out` бамперы, с ~25% шансом двойного `ad_in`
(вероятность в `DOUBLE_AD_IN_PROBABILITY`); общий "безразмерка"-бампер
(`kind='interstitial'`) вставляется между программами, когда рекламной паузы в
этот момент не было. Лимит 7 мин/час — `ad_pods.ad_seconds_in_trailing_hour`,
скользящее окно вместо приблизительного каданса; если бюджет исчерпан, пауза
просто пропускается (не откладывается на потом принудительно).

Сквозные тесты вскрыли два реальных бага, которых не было видно на уровне
отдельных функций: докладка перед техперерывом (`build_filler`, используется и
для затычки коротких промежутков внутри блока) не знала про часовой лимит
рекламы вообще — while-цикл мог упаковать намного больше 7 минут подряд;
и тот же `build_filler` подбирал бампер ЛЮБОГО вида как дозаполнение, из-за
чего `ad_in`/`ad_out` иногда попадали в эфир вне настоящего рекламного блока
(выглядело как "сейчас будет реклама", а её не было). Оба фикса — в
`ad_pods.build_filler`.

Проверено на реальной библиотеке (F:\REN-TV, 3 сгенерированных дня): Avatar/
Charodejki/Samurai Jack/TMNT идут строго по порядку серий; Beavers/Biker/
Smeshariki скачут непоследовательно (напр. S02E20 → S02E17); худший скользящий
час по рекламе — 344.5 сек (< 420); из 113 показов `ad_in` двойных — 27
(~24%, целевые 25%); вход в техперерыв — ровно к 05:00 МСК.

**Вывод (Фаза 6): локальное окно, не RTMP.** Решение пользователя — поток
смотрим локально, отдельным окном, без стриминга на внешнюю площадку. Через
`obs-websocket` это `OpenVideoMixProjector` (windowed-проектор на Program-микс);
живьём подтверждено — окно открывается и показывает текущий эфир.
`director/output_window.py`. Важный нюанс: это **разовое действие на сессию
OBS**, а не часть bootstrap в `run_playout.py` — проектор не персистентный
объект сцены (в отличие от источников/фильтров), и если открывать его при
каждом рестарте Director'а, окна будут копиться при каждом падении процесса,
хотя сам OBS не перезапускался.

**Устойчивость: watchdog-супервизор** (`director/supervisor.py`). Запускает
`run_playout` и `run_ticker` как дочерние процессы, раз в 5с проверяет
`proc.poll()`; при падении — перезапуск с экспоненциальным backoff (3с → 120с,
сброс до минимума после 60с стабильной работы), чтобы не устроить busy-loop,
если, например, OBS ещё не поднялся к моменту старта супервизора. Каждый
процесс логируется в свой файл в `logs/` (гитигнорится). Проектор открывается
один раз при старте самого супервизора — по той же причине, что и выше: OBS
не перезапускается вместе с упавшим дочерним процессом, значит открывать окно
надо на уровне супервизора, а не на уровне управляемых процессов. Живая
проверка: убил процесс `run_playout` через диспетчер задач — супервизор
заметил на следующем цикле поллинга и поднял новый с тем же логом.

**Ещё не сделано**: RTMP-вывод (не нужен — локальный вывод подтверждён как
финальное решение); многосуточный soak-тест (нужно реальное время, разово не
проверить в рамках сессии — практическая рекомендация: оставить супервизор
работать несколько дней и затем сверить `program_log`/логи на предмет дрейфа
или незамеченных падений).

## 5. Бегущая строка + Gemini

- Раз в 24 часа фоновая задача дёргает Gemini API с промптом, заточенным под стиль
  заголовков нулевых (желтоватый инфотейнмент/погода/анонсы/"скоро на канале" в духе
  начала 2000-х), получает пул из N строк.
- Пул кэшируется локально (TickerPool), ротируется в течение дня (например, каждая
  строка показывается несколько раз с интервалом, а не всё разом по кругу).
- Fallback: если API недоступен или вернул пустой/некорректный ответ — используется
  предыдущий кэш или статический резервный список.
- Рендер — browser source в OBS с марки-анимацией, Director пишет текущий
  список строк в локальный JSON/HTML, который читает источник.
